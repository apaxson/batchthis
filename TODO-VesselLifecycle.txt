TODO-VesselLifecycle
=====================
Plan for tracking a vessel's own lifecycle state (Clean/Ready -> Active ->
Needs Cleaning) and the timestamped transitions between those states,
independent of (but linked to) a vessel's detail page. Sketched
2026-09-20. This file is the reference to pick back up from.


STATUS (updated 2026-09-22)
---------------------------
IN PROGRESS - steps 1-8 of SUGGESTED ORDER OF WORK are done (2026-09-23:
Batch.transfer() + Out of Service). Remaining: the UI that calls
Batch.transfer() / Batch.complete() is tracked in TODO-BatchStage.txt
(MODEL CHANGES #5 and #6 - built during the batch workflow, plus an
ad-hoc "Transfer batch" action on batch.html for emptying a vessel that
has to go Out of Service mid-batch), and out-of-service vessel artwork.

Built so far:
* Vessel.status `choices=` + VesselStatusEvent model (migration 0030).
* `set_vessel_status()` in apps/batchthis/services.py - the single place
  status changes; status + event commit in one transaction.
* Batch create -> In Use (addBatch view); BatchAddForm only accepts a
  Clean/Ready fermenter (enforced on POST, not just the dropdown).
* `Batch.complete()` saves + -> Needs Cleaning. No UI calls it yet, on
  purpose: the "Complete Batch" action belongs to TODO-BatchStage.txt.
* `setActiveFermenter` signal deleted. Batch removed from Django admin
  (it bypassed the workflow).
* Vessel list page (/batchthis/vessels, React ModelTable + api/vessels/)
  and detail page (/batchthis/vessel/<pk>: status, time in status,
  capacity/fill, status history, current batch, status artwork).
  Sidebar "Fermenters (soon)" stub is now a live "Vessels" link.
* "Mark cleaned" action on the vessel detail page (POST
  vessel/<pk>/clean, optional notes) - only offered/allowed when the
  vessel is Needs Cleaning.
* batch.html "Current Vessel" panel links to the vessel detail page.
* Batch.vessel (nullable FK, migration 0032) = where the batch is NOW;
  Batch.fermenter stays the fermenter it started in. addBatch sets it.
  Older batches have it unset, so Batch.current_vessel and
  Batch.objects.in_vessel() fall back to fermenter.vessel.
* Batch.transfer(src, dst): any vessel type; dst must be Clean/Ready, src
  must be the batch's current vessel, batch must be active. src -> Needs
  Cleaning, dst -> In Use, batch.vessel -> dst, one "Transferred from
  [src] to [dst]" ActivityLog entry - all in one transaction. No UI yet.
* Batch.complete() now dirties batch.current_vessel (not the fermenter).
* Out of Service (STATUS_OUT) - see the section at the bottom.

Decisions made along the way:
* ActivityLog is for Batch actions only (incl. the BatchStage
  workflow). Vessel history lives only in VesselStatusEvent.
* The service function is named `set_vessel_status()` (not
  `log_vessel_status()`), since it changes state, not just logs it.

Known gaps / not in this plan:
* Batch Edit (batch/<pk>/edit) is broken - its POST creates a new
  batch. Separate bug, still open.
* Vessel is still registered in Django admin, so Vessel.status can be
  hand-edited there without an event.
* Existing vessels have no history before 2026-09-22 (events start from
  the first change after this shipped).

Companion to TODO-BatchStage.txt, which tracks a BATCH's production
stages (pitch -> fermentation -> aging -> filtering -> bottling). This file tracks a
VESSEL's physical state instead. The two are related (a batch entering
a vessel is part of why the vessel goes Active; a batch leaving/
completing is part of why the vessel goes to Needs Cleaning) but are
separate models/concerns - don't conflate them.


GOAL
----
* Give every Vessel a real, constrained status vocabulary instead of a
  free CharField, and an append-only, timestamped log of every status
  transition it goes through.
* Be able to answer "how long has this vessel been in its current
  state" and "what's this vessel's full history" (useful for cleaning
  cadence / maintenance tracking later).
* Build the first Vessel detail page (none exists today - Vessel is
  admin-only) to surface current status + history + current batch.
* Replace the existing buggy status-flipping signal with an explicit,
  correct service function, per CLAUDE.md's "prefer explicit service
  functions over signals" convention.


BUG FOUND ALONG THE WAY (this is what's silently broken today)
----------------------------------------------------------------
FIXED 2026-09-22: `setActiveFermenter` was deleted and replaced by explicit
`set_vessel_status()` calls (see STATUS above). Kept below for history.

`setActiveFermenter` (models.py:397-412), a post_save signal on Batch,
already attempts exactly this state-flipping and has two bugs:
  * Line 409: `if instance.fermenter.vessel.status is Vessel.STATUS_ACTIVE`
    uses `is` (identity) instead of `==` (equality) on strings. Works
    today only by luck of CPython string interning - not guaranteed.
  * Line 411: `instance.fermenter.save()` saves the wrong object - it
    should be `instance.fermenter.vessel.save()`. The vessel's
    `status = STATUS_DIRTY` assignment on line 410 is therefore set in
    memory and then silently discarded. The DIRTY transition never
    actually persists.
  * The code's own comment (models.py:407-408) already flags this:
    "this is a bad way to do this... Use a workflow or state-engine in
    the future." This plan IS that follow-up.


WHAT ALREADY EXISTS (don't re-invent these)
------------------------------------------------------------------
* `Vessel.status` (models.py:104) - free `CharField(max_length=15,
  default=STATUS_READY)`, no `choices=` constraint.
* Three status constants already defined on Vessel (models.py:100-102):
  `STATUS_ACTIVE = 'In Use'`, `STATUS_READY = 'Clean/Ready'`,
  `STATUS_DIRTY = 'Needs Cleaning'`. Reuse these verbatim - don't rename
  or introduce new labels.
* `BatchTest`/`BatchNote` (and the planned `BatchStageEvent` in
  TODO-BatchStage.txt) are the existing precedent for "append-only,
  timestamped, typed log entry against a parent object." A vessel
  status-transition log is structurally the same shape - copy this
  pattern again.
* `Batch.complete()` (models.py:378) and `Batch.transfer(src_vessel,
  dst_vessel)` (models.py:375, a `pass` stub) are the batch-lifecycle
  hooks that should trigger vessel status changes (vessel being
  vacated -> DIRTY). Same stub `Batch.transfer()` is also referenced by
  TODO-BatchStage.txt for racking/aging vessel moves - the two plans
  will need to agree on who implements it (see OPEN DECISIONS).
* Vessel-type status icon assets already added (commit 7b60d81):
  `aging-tank-{active,dirty,ready}.svg`, `brite-tank-{active,dirty,
  ready}.svg`, `wine-tank-{active,dirty,ready}.svg` in
  apps/batchthis/static/batchthis/img/ - 3 vessel "types" x 3 statuses.
  These were added ahead of any page that uses them; the new vessel
  detail page is presumably what they're for.
* Sidebar nav already has a "Fermenters" item marked "soon" (base
  template) - this is the natural landing spot for a vessel list/detail
  page once it exists.
* No Vessel detail view, URL, form, or template exists today - Vessel
  is registered in admin.py only (admin.py:8) and otherwise only ever
  reached indirectly via `batch.fermenter.vessel` (e.g. the "Current
  Vessel" panel just added to batch.html).


MODEL CHANGES
-------------
1. Add `choices=` to `Vessel.status` using the existing three
   constants (define a `STATUS_CHOICES` tuple on the class alongside
   them). No data change - existing rows already hold valid values.
   Cheap `AlterField` migration.

2. New `VesselStatusEvent` model:
   - vessel    = FK(Vessel, on_delete=CASCADE, related_name='status_events')
   - status    = CharField(choices=Vessel.STATUS_CHOICES)
   - timestamp = DateTimeField(default=timezone.now, editable=True)
                 # user-correctable, like BatchTest.datetime /
                 # BatchNote.date - NOT auto_now_add. (See the
                 # Batch.startdate auto_now_add bug documented in
                 # TODO-BatchStage.txt - don't repeat that mistake here.)
   - batch     = FK(Batch, null=True, blank=True, on_delete=SET_NULL)
                 # which batch (if any) drove this transition; symmetric
                 # to BatchStageEvent.vessel in the companion plan
   - notes     = CharField(max_length=250, blank=True)
   - Meta.ordering = ['timestamp']

3. `Vessel` convenience additions:
   - `current_status_event` property -> latest related VesselStatusEvent
   - `time_in_current_status()` -> elapsed time since that event's
     timestamp
   - Skip a denormalized "status changed at" cache field - `status`
     itself is already the current-value cache; don't add a second one
     speculatively.

4. [DONE] `set_vessel_status(vessel, status, batch=None, notes='')` service
   function (built in apps/batchthis/services.py, not views/main.py -
   it's called from model methods too): sets `vessel.status`, saves it, and creates the
   matching `VesselStatusEvent` row in one place. This is the single
   place status is ever allowed to change going forward.

5. Wire explicit calls to `set_vessel_status()`:
   - Batch creation / (re)assignment to a fermenter -> STATUS_ACTIVE
   - `Batch.complete()` and `Batch.transfer()` (implementation depends
     on OPEN DECISIONS below) -> STATUS_DIRTY on the vessel being
     vacated
   - New manual "Mark cleaned" action on the vessel detail page ->
     STATUS_READY (the only fully manual transition - nothing else
     rehydrates a vessel back to ready automatically, since actually
     cleaning it is a physical action)

6. Delete `setActiveFermenter` (models.py:397-412) and its signal
   registration in apps.py once the explicit call sites above cover
   its two cases. This removes both bugs along with the signal.

FOURTH STATE - OUT OF SERVICE (added 2026-09-22, BUILT 2026-09-23)
------------------------------------------------------------------------
Per Aaron: a vessel needs a fourth status for when it's pulled from use -
under repair, has a problem that needs fixing, or is decommissioned/
replaced. This is NOT part of the normal workflow (Clean/Ready -> In Use
-> Needs Cleaning -> Clean/Ready); nothing in the batch workflow sets or
clears it automatically. It's only set/cleared by hand, from a dedicated
Vessel state/management page.

To decide / watch out for before coding:
[x] Label + constant. RESOLVED by Aaron (2026-09-22): the label is
    "Out of Service" -> `STATUS_OUT = "Out of Service"` on Vessel. It's 14
    chars, so it fits the existing `max_length=15` on `Vessel.status` and
    `VesselStatusEvent.status` - no field widening needed, only the
    `choices=` AlterField migration (via makemigrations, never by hand).
[x] Repair vs. decommissioned: one state with notes, or two? A repaired
    vessel comes back; a decommissioned/replaced one never does. Options:
    - one "Out of Service" status + the reason in VesselStatusEvent.notes
    - "Out of Service" (temporary) + a separate `retired` flag / terminal
      "Decommissioned" status that hides the vessel from lists
    The history log should never be deleted either way - retire, don't
    delete, so old batches' VesselStatusEvent rows stay intact.
    RESOLVED (Aaron): one "Out of Service" status + reason, for now.
[x] Entry rules: block (or require confirmation) putting a vessel that's
    In Use with an active batch out of service - its batch would be
    orphaned. Likely only allowed from Clean/Ready or Needs Cleaning.
    RESOLVED (Aaron): only from Clean/Ready or Needs Cleaning. In Use is
    rejected - Batch.transfer()/complete() it (-> Needs Cleaning) first.
    Also rejected if an active batch is still in the vessel.
[x] Exit rules: returning to service probably goes to Needs Cleaning
    (safe default after a repair) rather than straight to Clean/Ready.
    This is the first real transition rule - set_vessel_status() accepts
    any status in v1, so these checks live in the management action (or
    trigger the "state machine enforcement" open decision above).
    RESOLVED (Aaron): returns to the status it had before going out.
    set_vessel_status() now records VesselStatusEvent.previous_status on
    every event; falls back to Needs Cleaning if unknown (e.g. hand-set
    in admin).
[x] Reason/notes required when taking a vessel out of service (reuse
    VesselStatusEvent.notes, make it required for this transition).
    RESOLVED (Aaron): required; logged as the VesselStatusEvent notes
    (vessel status history), not ActivityLog - ActivityLog stays
    batch-only.
